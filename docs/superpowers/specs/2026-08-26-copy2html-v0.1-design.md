# Copy2HTML v0.1 — Design Specification

## Status

Approved in design review on 2026-08-26.

## Product goal

Copy2HTML is a public, login-free browser application that converts copy authored in Word into clean, validated HTML ready to paste directly into a Liferay content module.

The primary workflow is:

`Word → Ctrl+C → Copy2HTML → Ctrl+V → small adjustments → Copy to Liferay → Liferay module`

VS Code is optional and is not part of the required publishing flow.

The core product is generic. Smiles is the first official preset pack and is active by default in v0.1, but no editor, serializer, sanitizer, or validation rule may be hard-coupled to Smiles-specific data.

## Scope

### In scope for v0.1

- Public application with no authentication.
- 100% client-side processing for copy, clipboard content, presets, and generated HTML.
- Visual rich-text editor.
- Real-time HTML output synchronized with the editor.
- Isolated preview of the final sanitized HTML.
- Word clipboard import with aggressive cleanup of Word-specific markup while preserving useful formatting.
- Base formatting controls.
- Official versioned preset packs.
- Smiles preset pack enabled by default.
- User-created custom presets persisted in `localStorage`.
- Liferay-compatible HTML as the only output mode.
- Validation before copying.
- Primary action labeled **Copy to Liferay**.
- Undo/redo and keyboard shortcuts.
- TDD coverage for sanitizer, serializer, clipboard conversion, presets, local persistence, editor interactions, and the main end-to-end flow.

### Explicitly out of scope for v0.1

- Authentication or user accounts.
- Database or application backend.
- Server-side processing of copy.
- Collaborative editing.
- Cloud sync of custom presets.
- JSX output.
- Alternative semantic HTML output modes.
- Direct write/publish integration with Liferay.
- DOCX file import.
- AI-based formatting decisions.
- Pixel-perfect recreation of the final Smiles production page in preview.

## Success criterion

A user must be able to open Copy2HTML, paste copy from Word, apply a small number of visual adjustments or presets, inspect the generated HTML and preview, validate the result, and copy HTML that is ready to paste directly into the Liferay module without opening VS Code.

## Technical approach

### Recommended stack

- Next.js
- TypeScript
- Tailwind CSS
- shadcn/ui
- Tiptap
- DOMPurify or an equivalent sanitization layer
- Vitest + Testing Library for unit/component tests
- Playwright for critical end-to-end flows

The application should remain deployable as a frontend-only Vercel project for v0.1.

## Architecture

The implementation is divided into four product domains plus versioned preset packs:

```text
src/
├── app/
│   └── ...
├── features/
│   ├── editor/
│   ├── preview/
│   ├── presets/
│   └── html-output/
├── core/
│   ├── clipboard/
│   ├── sanitizer/
│   ├── serializer/
│   ├── validator/
│   └── presets/
└── preset-packs/
    ├── base/
    └── smiles/
```

### Architectural rule

The following modules must remain generic:

- editor
- serializer
- sanitizer
- validator
- clipboard conversion

Smiles-specific colors, macros, snippets, labels, URLs, and formatting templates belong only to the Smiles preset pack.

A preset pack should expose structured capabilities rather than application logic. Conceptually:

```ts
interface PresetPack {
  id: string
  name: string
  formattingPresets: FormattingPreset[]
  linkPresets: LinkPreset[]
  insertionPresets: InsertionPreset[]
  snippetPresets: SnippetPreset[]
  previewTheme?: PreviewTheme
}
```

This boundary must allow additional packs to be added later without modifying the editor core.

## State and persistence

No global state library is required for v0.1.

The principal runtime state consists of:

- editor document state;
- active preset pack;
- custom user presets;
- output preferences that are relevant to Liferay HTML;
- validation state.

Official preset packs are versioned in the repository. User-created presets are stored in `localStorage` through a small storage abstraction so persistence behavior can be tested independently and replaced later if necessary.

Smiles is the default active pack on first launch. The user can switch packs or disable pack-specific presets.

## Editor UX

The main interface prioritizes publishing copy, not writing code.

### Primary areas

1. **Visual editor** — primary working area.
2. **Generated HTML** — synchronized output, visible but secondary.
3. **Preview** — isolated rendering of the final sanitized HTML.

The user must be able to complete the full v0.1 workflow without manually editing HTML.

### Base toolbar

The base product provides at least:

- bold;
- italic;
- link;
- remove formatting;
- single line break;
- double line break;
- undo;
- redo;
- preset search/access.

Preset packs extend available actions without changing the base editor implementation.

### Smiles preset categories

The initial Smiles pack should expose the sanitized, reusable patterns identified in the historical reference material.

#### Formatting

- Clube Smiles
- Cliente Smiles
- Diamante
- Clientes Ouro
- Cliente Prata
- standard strong emphasis
- small/observation text

#### Links and macros

- Clube Smiles membership macro
- promotion opt-in macro
- Clube Smiles page link

#### Insertions

- single break
- double break
- non-breaking space
- supported recurring HTML entities when useful

#### Structural snippets

Examples include:

- validity-period strip;
- Clube Smiles support copy with CTA.

Historical or context-dependent snippets must be marked as `review-before-use` and must not be silently applied as authoritative current standards.

## Clipboard and Word paste pipeline

Clipboard paste is a core feature, not a generic browser paste.

The pipeline is:

`Clipboard → parse → normalize → sanitize Word artifacts → editor document → serialize → final sanitize → validate`

### Clipboard source priority

1. Prefer `text/html` when available so useful formatting can be preserved.
2. Fall back to `text/plain` when HTML is unavailable or unusable.

### Word cleanup

The parser should remove or normalize Word-specific artifacts such as:

- `Mso*` classes;
- Microsoft-specific attributes and namespace data;
- inline font-family declarations that are not relevant to output;
- arbitrary margins and spacing from the source document;
- metadata and unsupported wrappers;
- redundant nested spans;
- empty formatting nodes.

The parser should preserve supported meaningful semantics where possible, including:

- strong/bold;
- italic;
- links;
- intended paragraphs;
- intended line breaks.

Word cleanup must be deterministic. v0.1 does not use AI to infer formatting intent.

## Serialization and output

The HTML displayed and copied to Liferay must be produced by the Copy2HTML serialization pipeline, not treated as arbitrary editor-generated HTML.

The serializer is responsible for producing predictable markup that matches the allowed Liferay output conventions.

The generated HTML updates in real time as the visual document changes.

The primary CTA is **Copy to Liferay**.

Before placing data on the clipboard, Copy2HTML must run the final sanitizer and validator and copy only the final sanitized result.

## Sanitization

Sanitization occurs at trust boundaries:

1. when importing external clipboard HTML;
2. before preview rendering;
3. before copying the final HTML.

The sanitizer uses an explicit allowlist of supported tags, attributes, style properties, URL schemes, and other constructs required by the supported Liferay workflow.

Unsupported executable content must never survive sanitization. This includes, at minimum:

- `<script>`;
- executable event-handler attributes such as `onclick`;
- unsafe URL schemes;
- unsupported embedded active content.

The sanitization layer must be independently unit tested.

## Validation

Validation is pragmatic and scoped to Copy2HTML-supported HTML. It does not claim to fully emulate Liferay's parser or runtime.

Validation results have three severities:

### Valid

No known issue was found in the supported output.

### Warning

The result can still be copied, but contains something worth reviewing, for example:

- unnecessary empty formatting elements;
- suspicious but allowed structure;
- a historical snippet marked for review.

### Blocked / sanitized

Unsafe or unsupported input was removed or transformed by the sanitizer. The UI must tell the user that content was removed or changed rather than silently implying the pasted source was preserved verbatim.

Validation should also detect supported cases such as:

- links without a usable `href`;
- disallowed style properties;
- unsupported tags or attributes;
- residual Word-specific markup;
- malformed preset configuration.

## Preview

The preview renders only the sanitized HTML.

It should run in an isolated `iframe` so application styles cannot accidentally affect the content preview and pasted content cannot affect the application shell.

For v0.1, preview fidelity is functional rather than pixel-perfect. Preset packs may provide a lightweight preview theme later without changing the preview engine.

## Preset system

### Official packs

Official packs are source-controlled and reviewed with the application.

The first official packs are:

- `base`
- `smiles`

### Custom presets

Users can create personal presets without authentication. They are stored locally in the browser.

Custom preset data must be validated before becoming executable formatting configuration. A custom preset cannot introduce script execution, event handlers, unsafe URLs, or arbitrary application code.

### Smiles seed

The existing sanitized preset seed derived from historical reference material can be used as the starting data set. Credentials and unrelated operational secrets from the historical source must never be copied into the repository or application bundle.

## Security and privacy

### Data flow

```text
Word
  ↓
Browser clipboard
  ↓
Copy2HTML client-side pipeline
  ↓
Browser clipboard
  ↓
Liferay
```

Copy content is not intentionally sent to Copy2HTML servers in v0.1.

No analytics or logging implementation may capture editor contents, clipboard payloads, generated HTML, or personal custom preset values.

### Repository hygiene

The repository must not contain credentials, passwords, VPN data, Microsoft credentials, customer secrets, or other sensitive values from historical reference files.

Only sanitized reusable technical presets may be committed.

## Error handling

Errors should be actionable and remain close to the affected workflow.

Examples:

- clipboard access unavailable → explain how to use standard paste/copy fallback;
- invalid custom preset → reject the invalid preset and identify the invalid field;
- unsafe pasted markup removed → show a sanitization notice;
- serialization failure → preserve editor content and prevent copying an incomplete result;
- localStorage unavailable → continue in-memory and warn that custom presets will not persist;
- preview rendering issue → keep editor and HTML output available even if preview fails.

No recoverable preview or persistence failure should destroy the current editor document.

## Testing strategy

Critical transformation logic follows TDD.

### Unit tests

- Word HTML normalization;
- clipboard parser;
- sanitizer allowlist and rejection cases;
- serializer output;
- validator severity and messages;
- preset schemas;
- Smiles official presets;
- custom preset validation;
- localStorage abstraction.

### Component/integration tests

- visual editor and generated HTML synchronization;
- selection + formatting preset application;
- selection + link/macro preset application;
- insertions such as single/double breaks;
- pack selection;
- custom preset persistence;
- validation feedback;
- Copy to Liferay behavior.

### Regression fixtures

Real, sanitized examples from the supplied workflow should become regression fixtures. The initial fixture must cover the support-copy scenario containing:

- `superbônus` as strong emphasis;
- `compra de milhas Smiles` as strong emphasis;
- `Clube Smiles` using the Smiles purple preset;
- `Assine agora` using the Clube Smiles membership macro and link styling;
- a double break between paragraphs.

Historical examples may be added only after removing credentials, personal information, unrelated identifiers, and customer-sensitive content.

### End-to-end test

The minimum v0.1 happy-path test is:

1. open the public application;
2. paste representative Word content;
3. confirm meaningful source formatting is preserved and Word-specific markup is removed;
4. select text and apply a Smiles formatting preset;
5. select CTA text and apply a Smiles link/macro preset;
6. inspect synchronized generated HTML;
7. inspect sanitized preview;
8. confirm validation is not blocking;
9. click **Copy to Liferay**;
10. assert that the clipboard contains the final sanitized expected HTML.

## Delivery principles

- Keep the implementation frontend-only for v0.1.
- Prefer deterministic transformations over inferred behavior.
- Keep domain boundaries small and independently testable.
- Do not introduce state libraries, backend infrastructure, authentication, databases, or AI unless a later requirement demonstrates the need.
- Do not hide transformations from the user: generated HTML remains inspectable even though manual code editing is optional.
- Optimize for the shortest reliable path from Word to Liferay.

## Future work, not commitments

Potential later versions may add:

- direct DOCX import and extraction of sections such as `[LP]`, `[TÍTULO]`, `[TEXTO]`, `[TARJA DE VIGÊNCIA]`, and `[RACIONAL]`;
- deterministic smart formatting suggestions;
- preset command palette and favorites;
- conversion history;
- additional output formats such as JSX;
- pack-specific preview themes;
- additional preset packs;
- optional direct Liferay integration if a safe and supported API workflow is available.

These items are intentionally excluded from the v0.1 implementation plan unless separately approved.
